## Verdict

**Le cœur n'a jamais été aussi solide — dix rounds d'audit à l'aveugle, un ledger de décisions discipliné, 140 tests verts, une architecture de convergence (stream + sweep + DLQ + 9 alarmes) qui est un modèle du genre. Mais le GO conditionnel du 27/08 reste conditionnel : C2 est fermée (CI verte), C1 et C3 sont ouvertes, et C4 s'est aggravée — le `.env` contient désormais des credentials de chaîne d'approvisionnement vraisemblablement actifs (2 PAT GitHub, 1 token crates.io), affichés pour la troisième fois dans une conversation d'audit. À rotationner aujourd'hui.**

S'y ajoutent deux défauts nouveaux nés de la phase « installable » (postérieure aux dix rounds) : `aithos verify <url>` est cassé, et le binaire distribué sur trois canaux pointe par défaut sur un hostname qui n'existe pas. Rien de tout cela ne touche le protocole ni la crypto — mais tout cela touche ce que le projet vend : la confiance vérifiable.

## 1. Les conditions du 27/08, une par une

### C1 — Zip Lambda périmé → **OUVERTE, et aggravée**

`target/lambda/registry.zip` date toujours du **26/08 05:36 UTC**. Trois versions coexistent désormais : le zip du dépôt (26/08, pré-reconciler, **pré-proofs**), l'environnement dev déployé (28/08 au matin — son manifest ne porte pas encore l'URL de dépôt corrigée de HEAD), et HEAD. Un `terraform apply` depuis l'état du poste déploierait un binaire qui : ignore `REGISTRY_EDGE_SECRET` (gate silencieusement absent), ne connaît ni `REGISTRY_ROLE=reconciler` ni `sweeper` (deux fonctions en échec de boot, pointeurs plus jamais convergés), et surtout **parle le protocole d'avant les publication proofs — la création redevient rejouable par quiconque lit une carte publiée** (le trou fermé en round 2, A-M2). C1 n'est plus une régression d'intendance : c'est une régression de sécurité en attente d'un apply.

**Faire** : `infra/build-lambda.sh` depuis HEAD, apply, e2e — puis traiter la cause : la CI ne produit toujours pas cet artefact (voir P1).

### C2 — CI jamais exécutée → **FERMÉE, vérifiée**

Le dépôt est public sur `github.com/aithos-protocol/registry`, la CI a tourné : run #1 rouge (renommage de paquet), **#2 et #3 verts au HEAD**, jobs `rust`, `audit` (cargo-deny seul, la leçon `deny.toml` a été retenue) et `terraform` (fmt + validate sans backend). La release #4 est verte, v0.1.0-alpha.1 publiée avec 6 assets + attestations de provenance. Réserve : voir I-f (pas de run planifié) et I-d (toolchain de release).

### C3 — Environnement prod inexistant → **OUVERTE, et désormais visible du public**

Toujours aucun `env/prod.tfvars`, et `registry.aithos.world` est **NXDOMAIN** — vérifié. Ce qui a changé : le CLI est maintenant **distribué** (crates.io — 11 téléchargements —, release GitHub, tap Homebrew) avec ce hostname en défaut. Voir I-b.

### C4 — Purger le réflexe `.env` → **OUVERTE, et aggravée : rotation immédiate requise**

`.env` est toujours là, modifié **ce matin** (29/08 05:16 UTC), et son contenu a changé de nature. Aux STS dev expirés (inertes) se sont ajoutés : un **PAT GitHub pour `aithos-protocol/registry`**, un **PAT pour `aithos-protocol/homebrew-tap`**, et un **token crates.io** — trois credentials longue durée, vraisemblablement actifs, en clair sur disque. Et l'histoire s'est répétée à l'identique : la commande d'inspection « masquée » de cet audit supposait du KEY=VALUE là où le fichier mélange JSON et lignes nues — les valeurs sont passées en clair dans une conversation d'audit **pour la troisième fois**, celle-ci comprise. `infra/ACCOUNT-SETUP.md` § « Do not » l'interdit noir sur blanc depuis le début.

La différence avec le 27/08 : des STS expirés ne coûtaient rien. **Un token crates.io permet de publier une version malveillante de `aithos` ; un PAT sur `registry` permet de pousser du code et des releases.** Ce sont les clés de la chaîne d'approvisionnement d'un outil qui manipule des clés privées.

**Faire aujourd'hui, dans l'ordre** : révoquer les deux PAT (GitHub → Settings → Developer settings) et le token crates.io ; supprimer `.env` ; ne plus jamais stocker ces tokens en fichier — `gh auth login` pour GitHub, `cargo login` (credential store) pour crates.io, secrets Actions pour la CI, SSO pour AWS. Puis lire I-e : l'objectif est que ces tokens n'aient plus besoin d'exister.

## 2. Constats nouveaux

### F1 — `aithos verify <url>` est inatteignable · **confirmé par exécution**

`crates/aithos-cli/src/main.rs` (`fetch_card`) : l'heuristique `looks_like_a_path` — contient `/`, commence par `.`, ou finit par `.json` — est évaluée **avant** le test `starts_with("https://")`. Toute URL contient `/` et celles des cartes finissent par `.json` : le mode URL, que `--help` documente (« An agent identifier, a URL, or a path to a card file »), tombe systématiquement en « no such file ».

```
$ aithos verify https://registry-dev.aithos.world/v1/agents/…/agent-card.json
aithos: https://…/agent-card.json: no such file      (exit 1)
```

C'est une régression introduite par deux correctifs successifs sur cette même fonction (le shadowing par fichier local de `2be4119`, puis la lecture bornée du round-10 m6) — le pattern « défaut introduit par le fix d'avant » que le ledger documente si bien ailleurs. L'échec est propre (fail closed, exit 1), donc fonctionnel, pas sécuritaire. Le contournement existe (agentId ou fichier local). **Faire** : tester le préfixe `https://`/`http://` avant l'heuristique de chemin ; ajouter le test unitaire qui manquait — aucun test ne couvre `fetch_card` sur une URL.

### F2 — Le binaire distribué pointe par défaut sur un hostname qui n'existe pas

`--registry` vaut `https://registry.aithos.world` (NXDOMAIN). Concrètement, pour quiconque installe l'outil aujourd'hui : `aithos whatis <id>` → `error sending request for url (…)` — l'erreur DNS brute de reqwest, sans un mot sur `--registry` ni `AITHOS_REGISTRY` ; et dès `aithos key new`, la ligne `agent https://registry.aithos.world/v1/agents/…` affiche une adresse qui ne résoudra pas. Le test Homebrew ne le voit pas : il n'exerce que le chemin offline.

**Faire** — c'est une décision produit liée à C3, trois options honnêtes : déployer prod avant toute annonce (la bonne, si l'ouverture est proche) ; ou changer le défaut vers `registry-dev` tant que prod n'existe pas (discutable pour un binaire déjà publié) ; a minima, attraper l'échec DNS sur le hostname par défaut et expliquer en une phrase que le registre public n'est pas encore ouvert et comment pointer ailleurs. L'option 3 est compatible avec les deux autres et coûte dix lignes.

### S1 — Le tag de release a été déplacé, et le clone local diverge

Les runs release #1–#3 (sur `f56275e`) ont été annulés, le #4 (sur `c04213f`) a produit la release : le tag distant `v0.1.0-alpha.1` pointe sur **`c04213f`**. Le tag local pointe toujours sur **`f56275e`**. Deux problèmes distincts :

- **Process** : un tag de release déplacé après coup est exactement l'antipattern que `gh attestation verify` existe à compenser — l'attestation reste juste (elle lie l'artefact au commit), mais « le tag » cesse d'être une référence stable, et un observateur qui a fetché tôt a une autre vérité qu'un observateur tardif. Pour un projet dont l'argument de vente est la provenance vérifiable, la règle doit être : un tag publié ne bouge jamais ; on re-tague `-alpha.2`.
- **Hygiène locale** : un `git checkout v0.1.0-alpha.1 && cargo build` sur ce poste ne reproduit pas la release publiée. `git fetch --tags --force` pour resynchroniser.

**Faire** : ruleset GitHub protégeant `v*` (interdire update/delete de tags — Repository rules le permet), et l'inscrire dans le commentaire de tête de `release.yml` qui documente déjà le reste du processus.

### P1 — L'artefact Lambda reste hors CI (la cause racine de C1)

`release.yml` construit et atteste le CLI pour cinq cibles — mais **aucun job ne construit `registry.zip`**, l'artefact qui fait tourner le service lui-même. Il continue d'être produit sur un poste (`build-lambda.sh`) et lu par Terraform depuis `target/`, sans lien vérifiable avec un commit : c'est le mécanisme qui a produit C1 deux fois. Ironie mesurable : le téléchargement du CLI est attestable, le service ne l'est pas.

**Faire** : un job (sur `ubuntu-24.04-arm`, ce que la matrice release utilise déjà) qui exécute `cargo lambda build --release --arm64 -p registry-lambda`, zippe, **atteste** (même mécanique `attest-build-provenance`) et publie l'artefact — en artefact de workflow horodaté lié au commit, ou mieux en objet S3 versionné que `var.lambda_package` sait consommer. Le jour où c'est en place, C1 devient structurellement impossible.

### P2 — La face « projet public » n'est pas au niveau du code

Pour un registre dont la promesse est la confiance, il manque autour du code : **pas de `SECURITY.md`** ni de canal de divulgation (la première personne qui trouvera une faille ouvrira une issue publique) ; description et topics GitHub vides ; **branch protection / tag protection à confirmer** (illisibles sans auth — et S1 suggère qu'il n'y a pas de tag protection) ; 2FA obligatoire sur l'organisation à confirmer ; publication crates.io par token local (voir C4) au lieu du **trusted publishing** (OIDC depuis Actions, supprime le token) ; le tap Homebrew poussé **à la main avec un PAT** ce matin, au lieu d'un job de release qui régénère la formule (le script `brew-formula.sh` existe déjà — il ne manque que le workflow et un secret scoped).

### I-f — `cargo deny` ne tourne qu'au push

Une advisory RUSTSEC publiée entre deux commits ne sera vue qu'au commit suivant — qui peut être dans un mois. Ajouter `schedule:` (hebdomadaire) au workflow `ci` pour le job `audit`, et l'e-mail d'échec fait le reste. Trois lignes.

### I-d — La release ne construit pas avec la toolchain épinglée (ou ne le dit pas)

Le step de `release.yml` s'appelle « Install the pinned toolchain » mais exécute `rustup toolchain install stable`. En pratique `rust-toolchain.toml` est présent au checkout et rustup moderne installe le pin à la volée — mais alors le step installe *stable* pour rien ; et si un runner a un rustup configuré autrement, la release build en stable pendant que la CI teste en 1.95.0. À trancher explicitement : `rustup show` (comme `ci.yml`) et un commentaire, pour que l'artefact atteste ce qu'on croit qu'il atteste.

### Mineurs

- **README § Development** : « 100 tests » — il y en a 140 (+4 e2e). Le chiffre était vrai à un moment ; le corriger ou, mieux, dé-chiffrer la phrase.
- **MSRV** : `rust-version = "1.90"` est déclarée (et publiée sur crates.io) mais jamais testée — la CI ne roule que 1.95.0. Un job MSRV, ou aligner la déclaration sur ce qui est réellement garanti.
- `check_registry` (CLI) : le test `ends_with('/')` est mort — `run()` fait `trim_end_matches('/')` avant tout appel. Cosmétique.
- **Restes infra connus et toujours ouverts** (hérités, non bloquants) : pas de logs d'accès CloudFront (les access logs API GW, eux, sont en place et bien conçus — `x-forwarded-for` compris) ; budget en `FORECASTED` seul (ajouter une notification `ACTUAL` : une ligne) ; `monthly_budget_eur` facturé en USD (renommer la variable) ; `alarm_email` passé en `-var` à l'apply — un oubli est silencieux (le README d'infra le documente ; une validation « prod ⇒ e-mail requis » serait plus sûre au moment de C3).
- **Hygiène du poste** : `_to_delete/` accumule des restes de sessions (deux tarballs, `gitobjs/`, `gitlocks/`) — supprimable ; et le dossier local s'appelle `agents-card-registery-2` (sic) quand le remote s'appelle `registry` — sans conséquence, juste déroutant.

## 3. Ce qui est solide (et re-vérifié aujourd'hui par exécution)

- **Le protocole et la crypto** : dix rounds à l'aveugle ont convergé — rounds 9 et 10 sans MAJOR, condition d'arrêt atteinte proprement. Les propriétés qui portent tout (thumbprint = kid signé, publication proofs liées au registre/identifiant/digest, Ed25519 `verify_strict` + refus des clés faibles, RSA en encodage minimal borné 2048–4096, refus de `crit`/`b64`, parsing strict anti-doublons jusque dans les headers, `precedence()` SemVer) sont dans le code **et** testées — 140 tests verts re-exécutés, clippy muet, wasm OK.
- **La convergence du chemin public** : un seul écrivain logique (une fonction, deux déclencheurs), stream filtré `CURRENT` + `TRIM_HORIZON` + batch 1 + 5 retries + DLQ SQS 14 j, sweep horaire borné, garde anti-rollback par `seq` stampé sur les deux pointeurs, relecture pré-écriture contre la résurrection post-retrait, et l'asymétrie d'ordre publish/withdraw raisonnée dans les deux sens. Vérifié live : carte et JWKS d'un agent retiré → 404 au bord, record 200 `WITHDRAWN`, historique intact.
- **L'IAM** : trois rôles, chacun exactement ses appels (l'API sans aucun delete nulle part ; le reconciler sans lecture de table hors `GetItem` unitaire ; le sweeper read-only sur le registre) — relu appel par appel, rien à redire.
- **Le bord** : WAF trois règles (writes/IP, writes/agentId avec `URL_DECODE` réfléchi, requests/IP) répondant 429 en corps problème ; edge gate en comparaison constante, requis au boot ; comportements CloudFront ordonnés avec les pièges (wildcards trans-slash, 404 custom, conditionnels non forwardés sur l'immuable) documentés là où ils mordent.
- **L'hygiène git** : `.env` jamais commité (re-vérifié), zéro secret dans tout l'historique (grep AKIA/ASIA/PAT/clés privées : 0), `Cargo.lock` committé, `deny.toml` justifié ligne à ligne.
- **Le CLI, là où les rounds sont passés** : keyfile JWE exemplaire (PBES2 600k itérations plafonnées, header en AAD, `create_new` 0600, zeroize honnête sur ses limites), `check_provers` qui explique avant que le serveur ne refuse, sorties `whatis`/`verify` qui séparent l'établi du déclaré — la doctrine anti-phishing est dans le produit, pas seulement dans la SPEC.
- **La méthode elle-même** : `audits/LEDGER.md` — 146 décisions, y compris les refus motivés (« do not re-raise ») — est la meilleure garantie que ce niveau se maintienne. Peu de dépôts de cette taille ont cet outillage.
