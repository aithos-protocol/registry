# Audit de mise en production — Agent Card Registry

**Date** : 26 août 2026 · **Périmètre** : workspace Rust (4 crates), Terraform `infra/`, hygiène du dépôt · **Méthode** : lecture intégrale du code et de l'infra, exécution de la suite de tests (74 tests), clippy, `cargo audit`, sondes DoS écrites pour l'audit, vérification des sources des dépendances critiques (`rsa`, `axum`), vérification documentaire AWS (corps des requêtes DELETE via CloudFront).

---

## Verdict

**NO-GO pour une production ouverte au public aujourd'hui — mais GO pour un déploiement dev/interne, et le GO production est proche.**

Le cœur protocolaire (canonicalisation RFC 8785, JWS, thumbprints RFC 7638, règles d'autorisation) est d'une qualité rare : je n'y ai trouvé **aucune faille d'autorisation, aucune boucle infinie, aucun panic exploitable, aucun `unsafe`**, et les surfaces de DoS classiques (bombe de profondeur JSON, clés RSA géantes, corps illimités, confusion d'algorithmes, `alg:none`, rejeu) sont toutes fermées — je les ai testées, pas seulement lues.

Ce qui bloque n'est pas la crypto : ce sont **trois écarts entre le code et l'infra de lecture publique**, dont un qui casse une promesse normative de la SPEC (le retrait), et l'absence de garde-fous de coût par source. Trois correctifs ciblés, un test d'intégration contre une vraie table, et le lancement est défendable.

---

## 1. Bloquants avant production (B)

### B1 — Le retrait (withdrawal) ne purge jamais le chemin de lecture public · **Sévérité : haute**

- `edge.tf:79-97` route `/v1/agents/*/agent-card.json` et `/v1/agents/*/jwks.json` vers **S3 directement** ; le Lambda ne voit jamais ces requêtes.
- `aws_store.rs::withdraw()` ne touche **que DynamoDB** ; les objets pointeurs `v1/agents/{id}/agent-card.json` et `jwks.json` restent dans S3.
- L'IAM (`compute.tf:47-52`) n'accorde **pas `s3:DeleteObject`** (choix délibéré et documenté), et le retrait étant **terminal** (§6.5 : l'agentId n'est jamais réutilisable), aucune publication future n'écrasera jamais ces pointeurs.

**Conséquence** : après un `DELETE` réussi (200, statut WITHDRAWN en base), la carte retirée et son JWKS restent servis **indéfiniment** sur les URL publiques principales. La SPEC §7.1 promet `410 Gone` ; le Lambda l'honore, mais CloudFront ne route jamais ces chemins vers lui. La seule raison d'être du retrait — permettre au détenteur de clé de dépublier sans opérateur — est défaite sur le chemin chaud. Sujet de confiance et potentiellement de conformité (droit de retrait de données publiées).

**Pistes** (une suffit) :
1. `withdraw()` **écrase** les deux pointeurs avec un tombstone JSON (problème RFC 9457 `WITHDRAWN`) + `CreateInvalidation` CloudFront — ne demande que `PutObject` déjà accordé + `cloudfront:CreateInvalidation` ; le statut HTTP restera 200 côté S3, à documenter, ou
2. supprimer les pointeurs (accorder `DeleteObject` restreint au préfixe `v1/`) + invalidation → S3 renverra 403/404, ou
3. le correctif que le README identifie déjà : un handler **DynamoDB Streams** qui réconcilie les pointeurs depuis la table (résout aussi B3).

### B2 — Aucune limitation de débit par source : attaque au portefeuille et pollution illimitée · **Sévérité : haute**

La SPEC §8 annonce « Write rate limits are per source address and per `agentId` » — **rien ne l'implémente**, ni dans le code, ni dans l'infra. Le seul garde-fou est le throttle **global** API Gateway (`compute.tf:120-123` : 20 rps, burst 50), partagé entre toutes les routes et toutes les sources.

Le design « la clé est le compte » rend la création d'identités **gratuite et illimitée** (une paire Ed25519 se génère en microsecondes, hors ligne). Un attaquant qui sature le throttle à 20 rps avec des cartes de 256 KiB :

- ~1,7 M écritures/jour, chacune stockée **pour toujours** (S3 versions + item DynamoDB + entrée GSI) ;
- jusqu'à ~**13 To/mois** de croissance S3 théorique, plus les WCU DynamoDB transactionnelles (×2) et 2-3 PUT S3 par écriture — un coût récurrent de l'ordre de plusieurs centaines d'euros/mois qui **ne redescend jamais** (append-only + pas de droit de suppression) ;
- accessoirement, un listing public inondé d'entrées poubelles.

**Pistes** : WAF (règle rate-based par IP sur PUT/DELETE, ex. 10 req/5 min) devant CloudFront ou l'API ; alarme AWS Budgets (prescrite par `ACCOUNT-SETUP.md` §5 mais créée à la main — la vérifier avant ouverture) + alarme CloudWatch sur le count d'invocations Lambda ; à terme un compteur par IP/`agentId` dans DynamoDB (TTL). Le throttle global actuel borne le pire cas — c'est bien — mais il ne distingue pas l'attaquant du trafic légitime : à 20 rps l'attaquant obtient aussi un **déni de service des écritures légitimes** à coût quasi nul.

### B3 — Pointeurs « current » : rafraîchissement non ordonné, échec silencieux en pratique · **Sévérité : moyenne-haute**

`aws_store.rs::refresh_current_pointers()` s'exécute **après** la transaction, sans ordre garanti entre deux publications rapprochées : le refresh du seq 2 peut s'appliquer **après** celui du seq 3, laissant CloudFront servir une carte périmée jusqu'à la prochaine publication (qui peut ne jamais venir). L'échec est loggé « loudly » (`tracing::error!`) — mais **aucune metric filter, aucune alarme** n'existe dans l'infra : en pratique personne ne le verra. Cas aggravé : si le refresh échoue à la **création**, le chemin chaud renvoie une erreur S3 brute (403 AccessDenied XML) jusqu'à la prochaine version.

**Pistes** : le handler Streams du README (règle B1+B3 d'un coup) ; a minima avant lancement : metric filter CloudWatch sur ce log d'erreur + alarme, et re-lecture du seq avant PUT du pointeur pour réduire la fenêtre d'inversion.

## 2. Correctifs importants, non bloquants (I)

**I1 · Idempotence contredite.** SPEC §6.1 : « submitting identical bytes twice yields the same stored version » (justifie l'absence d'Idempotency-Key). Le code renvoie **409 VERSION_NOT_INCREASING** au resoumis identique (test `resubmitting_the_same_version_is_refused` le verrouille). Un client qui retente après un timeout réseau — le cas normal sur Lambda — reçoit une erreur pour une écriture qui a réussi. Renvoyer 200 quand `digest == current` (ou corriger la SPEC).

**I2 · `GET /versions` sans pagination.** `aws_store.rs::list_versions()` fait **une seule** Query DynamoDB : au-delà de ~1 Mo d'items (~3-4 000 versions), la liste est **tronquée silencieusement** (pas de suivi de `LastEvaluatedKey`, pas de curseur dans l'API). Un publieur peut créer des milliers de versions légitimement (0.0.1, 0.0.2…).

**I3 · Des octets jamais commités restent servis.** `commit()` écrit l'objet S3 **avant** la transaction (ordre justifié) ; en cas d'échec de la transaction, l'orphelin est « harmless » — sauf que `get_version_card` sert S3 **sans vérifier** que la version existe en base. Scénario réel : une clé compromise perd une course de rotation, mais sa carte (validée contre l'instantané pré-rotation) reste téléchargeable à l'URL immuable par quiconque connaît le digest. Vérifier l'item VERSION# avant de servir, ou documenter l'invariant.

**I4 · JWKS d'un agent retiré.** `get_jwks` renvoie 200 avec les clés après retrait (côté API ; côté S3 c'est B1). La carte renvoie 410, le JWKS devrait suivre.

**I5 · Curseurs forgés → 500.** `decode_cursor` mappe toute erreur sur `StoreError::Backend` → **500 INTERNal**, et un curseur bien formé mais faux déclenche une ValidationException DynamoDB → 500 aussi. Entrée attaquable qui pollue les alarmes 5xx : renvoyer 400.

**I6 · Dépendances (cargo audit : 5 avis).** Aucun exploitable dans ce déploiement, à documenter et suivre : `rsa 0.9.10` RUSTSEC-2023-0071 (Marvin — opérations **privées** uniquement ; le registre ne fait que vérifier : accepté) ; `h2 0.3.27` et `rustls-webpki 0.101.7` (3 avis) via la pile héritée hyper 0.14 de `lambda_http` — côté **client sortant** vers les endpoints AWS, pas exposé aux requêtes entrantes ; `lru` (unsound, interne SDK AWS). Ajouter `cargo audit`/`cargo deny` en CI et bumper quand `lambda_http` migre.

**I7 · Pas de CI.** Aucun workflow : tests/clippy/fmt/audit ne sont exécutés que sur un poste. `cargo fmt --check` échoue d'ailleurs (un diff cosmétique dans `keys.rs:82`). Le zip Lambda est construit localement sans provenance. Une CI GitHub Actions de 20 lignes ferme tout ça.

**I8 · Observabilité minimale.** Pas d'access logs API Gateway, pas de logs CloudFront, aucune alarme (cf. B3). Avant d'ouvrir : logs d'accès API GW + alarmes 5xx/throttle/facturation.

**I9 · Lifecycle S3.** Versioning activé + pointeurs `current` réécrits à chaque publication = versions non courantes qui s'accumulent sans règle d'expiration. Une lifecycle rule `noncurrent 30-90 j` sur le préfixe `v1/` (les `versions/…` sont immuables, jamais réécrits — non concernés).

**I10 · Identifiants AWS en clair dans `.env`.** Le fichier contient des credentials STS **temporaires** étiquetés `aithos-prod` (expiration aujourd'hui 08:30 UTC). Points positifs : `.gitignore` les couvre, jamais commités, pas de remote git. Mais `ACCOUNT-SETUP.md` § « Do not » l'interdit explicitement — à raison. À savoir : ma commande d'inspection du fichier en a affiché le contenu dans cette conversation ; ils expirent d'eux-mêmes ce matin, mais par principe : révoquer les sessions actives du permission set si encore valides, et ne plus stocker de credentials dans l'arborescence du projet (profils SSO uniquement, `aws sso login`).

## 3. Notes mineures (N)

- **N1** — Agent inconnu sur le chemin chaud : S3 renvoie 403 AccessDenied en XML brut (pas de `custom_error_response` CloudFront). Cosmétique mais visible publiquement.
- **N2** — `jws.rs:96` : le rejet de `jku` contenant `@` refuse aussi des URL légales (`@` en path/query). Déviation mineure de §5.7, dans le sens sûr.
- **N3** — SPEC §6.5 et tests utilisent `registry.aithos.be`, l'infra `registry-dev.aithos.world` : harmoniser l'exemple de la SPEC.
- **N4** — Clés RSA : pas de borne supérieure dans `Jwk::parse`, mais le crate `rsa` plafonne à 4096 bits et borne l'exposant (vérifié dans les sources 0.9.10) — coût borné, rien à faire.
- **N5** — CloudFront transmet bien le corps des requêtes DELETE (vérifié docs AWS) — le retrait *via* CloudFront fonctionnera ; mais **aucun déploiement réel n'a encore eu lieu** (le README le dit) : dérouler le smoke test + un test d'intégration contre une vraie table avant la première carte réelle, en particulier `TransactWriteItems` conditionnel et le GSI.

## 4. Ce qui est solide (et vérifié)

- **Autorisation** : la règle `kid = thumbprint RFC 7638` est correctement implémentée et rend la substitution de clé impossible ; allowlist d'algorithmes vérifiée avant toute crypto ; confusion d'algorithme fermée par le binding type de clé ↔ alg ; `alg:none`, `crit`, `b64:false`, membres inconnus du header : tous rejetés (testés).
- **Rejeu** : version semver strictement croissante ; retrait lié au digest courant et à l'origine du registre (testés).
- **Concurrence** : écritures conditionnelles DynamoDB (TransactWriteItems + `attribute_not_exists` / `seq = :expected`), contrat `Conflict` propre, magasin mémoire qui reproduit le même contrat pour les tests.
- **DoS** : corps borné à 2 Mo (limite axum vérifiée dans les sources) puis 256 KiB canonique ; 8 clés / 8 signatures max ; bombe de profondeur JSON → erreur propre à 128 niveaux (sondé jusqu'à 10 000 niveaux sans crash) ; parse plat de 2 Mo < 1 s ; timeout Lambda 15 s ; retries SDK bornés. **Aucune boucle non bornée dans tout le code.**
- **Parsing strict** : doublons de membres rejetés, entiers hors I-JSON rejetés, `-0`/`1e21`/`1e-7` canonicalisés conformément à RFC 8785 (sondé) ; vecteurs officiels RFC 8785, exemple travaillé A2A §8.4.1, exemple RFC 7638, carte échantillon A2A §8.5 : tous joués par la suite, plus un test différentiel contre une seconde implémentation.
- **Infra** : S3 privé (public access block + OAC + condition `AWS:SourceArn`), chiffrement, versioning ; DynamoDB PITR + deletion protection + `prevent_destroy` ; IAM minimal **sans aucun droit de suppression** ; pas de secrets dans l'environnement Lambda ; `REGISTRY_ORIGIN` issu de la config, pas du header Host ; TLS ≥ 1.2 ; logs CloudWatch avec rétention 30 j ; état Terraform verrouillé et chiffré.
- **Qualité** : 74 tests verts (+ 5 sondes d'audit), clippy sans avertissement, zéro `unsafe`, zéro panic sur les chemins de requête, erreurs RFC 9457 avec pointeurs JSON précis, documentation interne exceptionnelle.

## 5. Coûts en régime normal

À l'arrêt ou à faible trafic : ~1-2 €/mois (zone Route 53, logs, stockage). Lectures servies par CloudFront/S3 au coût CDN standard. Le profil de coût ne dérape que sous l'attaque décrite en B2 — d'où son statut bloquant, l'alarme Budgets étant aujourd'hui le seul filet et sa présence non vérifiable depuis ce dépôt.

---

## Séquence recommandée avant ouverture

1. B1 (retrait → purge des pointeurs, idéalement via le handler Streams qui règle aussi B3) ;
2. B2 (WAF rate-based + vérifier l'alarme Budgets + alarmes CloudWatch) ;
3. I1 (idempotence du resoumis identique) — trivial et évite de vrais incidents clients ;
4. déploiement dev + test d'intégration live (N5), puis I2-I5 au fil de l'eau.

Le reste peut suivre le lancement sans risque.
